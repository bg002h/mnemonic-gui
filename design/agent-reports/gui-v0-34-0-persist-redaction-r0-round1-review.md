## Important

**I1 — §4 / Non-goals load-bearing claim "the toolkit has zero positionals" is FALSE (measured against the pinned binary).** `mnemonic 0.53.1`'s `gui-schema` emits non-empty `positionals` for **7 subcommands**: `decode-address` (`address`, required), `inspect` / `repair` / `verify-bundle` (`extra_strings`, repeating), and `xpub-search-{account-of-descriptor,passphrase-of-xpub,path-of-xpub}` (`positional`, repeating). At least four are **secret-capable**: `mnemonic inspect --help` documents the positional as HRP-autodetect `[STRING]...` intake that routes **ms1** (master-secret) alongside mk1/md1, and `mnemonic xpub-search passphrase-of-xpub --help` documents `[MS1]...` "Positional ms1 card". The claim's source is the **stale doc-comment** `src/schema/mod.rs:40-42` ("mnemonic-toolkit's subcommands have zero positionals"), contradicted GUI-internally by `src/schema/mnemonic.rs:3215` (`DECODE_ADDRESS_POSITIONALS` — which §0's own census counts as "mnemonic 1"; §0 and §4 contradict each other). The spec's *conclusion* (no toolkit gui-schema companion, no schema_mirror impact) survives, but for different reasons that must be stated: (a) gui-schema's positional objects carry only `name`/`required`/`repeating` — no `secret` field exists toolkit-side to mirror; (b) the schema_mirror gate compares flag names only (`parse_gui_schema_json` extracts flag names; `tests/schema_mirror.rs` never compares positionals); (c) the GUI hand schema deliberately mirrors only decode-address (30× `NO_POSITIONALS`). **Fix:** re-derive §4's no-companion claim from those measured facts; correct `mod.rs:40-42` in-cycle; reword the Non-goal ("hypothetical future toolkit positional (zero exist)" — seven exist now, unmirrored); file/note a FOLLOWUP for the unmirrored secret-capable toolkit positionals, including the mixed-secrecy wrinkle (HRP-autodetect positionals are value-dependent secret → a schema-level `secret: bool` must be conservatively `true` if ever mirrored).

**I2 — §2 allowlist has a leak-direction false-accept class: byte 0 is unconstrained.** "`pub` at bytes 1..4 after origin-strip" accepts ANY string with `p`,`u`,`b` at offsets 1-3. Base58 includes all three, so a WIF of the form `Kpub…`/`Lpub…`/`5pub…`/`9pub…`/`cpub…` is syntactically valid and would survive `blank_non_extended_public_keys` in cleartext (~58⁻³ ≈ 1/195k per random key). The deny-list's identical looseness (`is_xprv_like`, `tree_model.rs:651-654`) was safe because its false-positives over-BLANK (harmless); mirroring it into an allowlist inverts the failure cost to a persist leak — "exact complement of the `prv` probe" is the wrong design target for the fail-closed direction. **Fix (one byte-check):** additionally require byte 0 ∈ the extended-public first-char set `{x,t,y,Y,z,Z,u,U,v,V}` (disjoint from WIF first chars K/L/5/9/c), or match the full 4-byte prefix against the literal `xpub/tpub/ypub/Ypub/zpub/Zpub/upub/Upub/vpub/Vpub` list; add a T5 row `Kpub<base58…>` → BLANKED.
